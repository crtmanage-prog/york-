## Что это за проект

Онлайн-школа английского языка YORK! в Уфе. Полностью веб-платформа:
сайт + личные кабинеты + Telegram-бот. Никакого мобильного приложения
нет (обсуждали, отложили).

## Архитектура — важно понимать, прежде чем что-то менять

- **Никакого фреймворка и сборки.** Голый HTML/CSS/JS в одном файле на
  страницу. Библиотека Supabase встроена инлайн в `admin.html`,
  `teacher.html`, `cabinet.html` (полноценный JS SDK), но **не** в
  `trial-form.html` — там прямые `fetch()`-запросы
  к REST API Supabase, без SDK. Это осознанный выбор для публичных
  анонимных форм, не ошибка — не пытайся «исправить» на SDK.
- **Хостинг — GitHub Pages**, статические файлы напрямую из репозитория.
  Никакого серверного рендеринга.
- **Backend — Supabase.** URL и ключ (anon, публичный, можно светить в
  клиентском коде):
  ```
  SUPABASE_URL = 'https://uuwtarchkltdmaddndgm.supabase.co'
  SUPABASE_ANON_KEY = 'sb_publishable_jlcvNafksQ0WhrYCY08anw_ju194-I9'
  ```
- **Часовой пояс школы — `Europe/Moscow` (МСК)** (константа `SCHOOL_TZ`
  почти везде). Все данные о времени уроков и доступности хранятся в
  этом поясе в базе — это внутренний «единый язык» всей платформы.
  Отображение в личном поясе конкретного человека (ученика) — это
  ТОЛЬКО слой поверх, при отображении, а не то, как хранятся данные.
  Не путай эти две вещи при работе с датами.
  Раньше школа жила по Уфе/Екатеринбургу (UTC+5); в октябре 2026 всё
  переведено на МСК: часы доступности/пожеланий сдвинуты на −2, cron и
  тексты уведомлений пересчитаны, везде подпись «МСК». Слово «Уфа» как
  время школы больше не используем.
- **Telegram-бот (@weyorkonlinebot) разрабатывается ОТДЕЛЬНО**, другим
  Claude-инстансом/сессией, через Supabase Edge Functions
  (`telegram-webhook`). Если работаешь в Claude Code над сайтом — не
  трогай бот-функции напрямую, координируйся через файлы-брифы (см.
  раздел про бота ниже).

## Известные болевые места и договорённости

- **Всегда проверяй реальное состояние, а не верь, что файл «залит».**
  За время проекта несколько раз бывало, что сгенерированный файл или
  миграция не долетали до продакшена, а на словах считались применёнными.
  Если есть способ проверить напрямую (запрос к базе, чтение файла из
  репозитория) — проверяй, не полагайся на «должно быть сделано».
- **Storage-политики Supabase — отдельный слой от обычных RLS на
  таблицах.** Была ошибка: учитель не мог скачать файл домашки ученика,
  потому что политика в Storage разрешала читать файл только из своей же
  папки (`storage.foldername(name)[1] = auth.uid()`), без учёта роли
  учителя. Если чинишь доступ к файлам — проверяй именно
  `storage.objects`, не только таблицы.
- **Не делай тихих отказов.** Несколько раз находили баги, где ошибка
  (загрузка файла, скачивание) просто ничего не делала без сообщения
  пользователю. Всегда показывай понятную ошибку, если что-то не
  получилось — молчаливый сбой хуже явного.
- **Бот и сайт должны использовать одну и ту же бизнес-логику.**
  Например, подсчёт остатка занятий в абонементе — есть точная формула
  в `cabinet.html` (`computeRemaining`), и если бот считает то же самое —
  должен использовать идентичную логику, а не собственную. Расхождение
  в цифрах между ботом и кабинетом подрывает доверие.
