Этот файл — общий контекст проекта для Claude Code. Прочитай целиком перед
тем, как что-то менять — здесь собраны договорённости, которые сложились

## Что это за проект

Онлайн-школа английского языка YORK! в Уфе. Полностью веб-платформа:
сайт + личные кабинеты + Telegram-бот. Никакого мобильного приложения
нет (обсуждали, отложили).

## Архитектура — важно понимать, прежде чем что-то менять

- **Никакого фреймворка и сборки.** Голый HTML/CSS/JS в одном файле на
  страницу. Библиотека Supabase встроена инлайн в `admin.html`,
  `teacher.html`, `cabinet.html` (полноценный JS SDK), но **не** в
  `trial-form.html` и `reschedule.html` — там прямые `fetch()`-запросы
  к REST API Supabase, без SDK. Это осознанный выбор для публичных
  анонимных форм, не ошибка — не пытайся «исправить» на SDK.
- **Хостинг — GitHub Pages**, статические файлы напрямую из репозитория.
  Никакого серверного рендеринга.
- **Backend — Supabase.** URL и ключ (anon, публичный, можно светить в
  клиентском коде):
  ```
  SUPABASE_URL = 'https://uuwtarchkltdmaddndgm.supabase.co'
  SUPABASE_ANON_KEY = 'sb_publishable_jlcvNafksQ0WhrYCY08anw_ju194-I9'
  ```
- **Часовой пояс школы — `Asia/Yekaterinburg`** (константа `SCHOOL_TZ`
  почти везде). Все данные о времени уроков и доступности хранятся в
  этом поясе в базе — это внутренний «единый язык» всей платформы.
  Отображение в личном поясе конкретного человека (ученика) — это
  ТОЛЬКО слой поверх, при отображении, а не то, как хранятся данные.
  Не путай эти две вещи при работе с датами.
- **Telegram-бот (@weyorkonlinebot) разрабатывается ОТДЕЛЬНО**, другим
  Claude-инстансом/сессией, через Supabase Edge Functions
  (`telegram-webhook`). Если работаешь в Claude Code над сайтом — не
  трогай бот-функции напрямую, координируйся через файлы-брифы (см.
  раздел про бота ниже).

## Файлы и что они делают

**Публичные страницы (маркетинг/воронка):**
- `index.html` — главная страница школы
- `trial-form.html` — форма записи на бесплатный пробный урок. Самая
  чувствительная публичная форма: анти-спам (honeypot + таймер 3 сек),
  обязательный выбор часового пояса, выбор преподавателя (либо
  конкретный, либо «Не важно» — тогда показывается объединённая
  доступность всех реальных преподавателей), подключение Telegram-бота
  по токену после отправки.
- `talk-club.html` — отдельный продукт, разговорный клуб
- `level-test.html` — тест на уровень английского
- `privacy-policy.html` — политика конфиденциальности (статус: физлицо!)
- `avito.html` — черновая посадочная под трафик с Авито, сейчас не
  используется в реальной схеме (Катерина ведёт цены текстом в самом
  объявлении и шлёт ссылку сразу на `trial-form.html`)

**Личные кабинеты (за логином, полный Supabase JS SDK):**
- `login.html` — статичная страница выбора роли, просто ссылки на
  cabinet/teacher/admin, сама ничего не запрашивает у Supabase
- `cabinet.html` — кабинет ученика: расписание, домашка (три состояния:
  отметить выполненным без файла / прикрепить файл или ссылку), прогресс,
  реферальная программа
- `teacher.html` — кабинет учителя: занятость, ученики, проверка домашки,
  зарплата
- `admin.html` — админка Катерины: заявки на пробный, ученики,
  преподаватели, расписание, оплаты, статистика, рефералы, «Добавить
  человека» (с автоподстановкой часового пояса из заявки на пробный)

**Отдельная страница вне личного кабинета:**
- `reschedule.html` — самостоятельный перенос урока учеником. Открывается
  по одноразовому токену из Telegram-бота (НЕ через логин). Токен живёт
  в таблице `reschedule_tokens`, резолвится функцией
  `resolve_reschedule_token(p_token)`. Полный флоу: ученик выбирает один
  из двух ближайших уроков → до двух желаемых слотов из реальной
  доступности преподавателя → заявка уходит в `reschedule_requests` →
  учитель через бота подтверждает/отклоняет/предлагает своё → финальное
  решение всегда за Катериной (админом), не за учителем.
  `reschedule-editorial-york.html` — визуальный редизайн той же страницы,
  функционально идентичен `reschedule.html`.

**Черновики/варианты, НЕ живые страницы** (не путать с боевыми файлами):
`login-v1-chips.html`, `login-v2-blob.html`, `login-v3-grid.html`,
`index-redesign-preview.html`, `index-rebrand-preview.html`,
`animation-variants.html`, `york-website.html`, `york-english-test.html`,
`york-flyer-a6.html` — это черновики для сверки дизайна, никогда не
заливались на прод как есть.

## Известные болевые места и договорённости

- **Всегда проверяй реальное состояние, а не верь, что файл «залит».**
  За время проекта несколько раз бывало, что сгенерированный файл или
  миграция не долетали до продакшена, а на словах считались применёнными.
  Если есть способ проверить напрямую (запрос к базе, чтение файла из
  репозитория) — проверяй, не полагайся на «должно быть сделано».
- **Storage-политики Supabase — отдельный слой от обычных RLS на
  таблицах.** Была ошибка: учитель не мог скачать файл домашки ученика,
  потому что политика в Storage разрешала читать файл только из своей же
  папки (`storage.foldername(name)[1] = auth.uid()`), без учёта роли
  учителя. Если чинишь доступ к файлам — проверяй именно
  `storage.objects`, не только таблицы.
- **Не делай тихих отказов.** Несколько раз находили баги, где ошибка
  (загрузка файла, скачивание) просто ничего не делала без сообщения
  пользователю. Всегда показывай понятную ошибку, если что-то не
  получилось — молчаливый сбой хуже явного.
- **Бот и сайт должны использовать одну и ту же бизнес-логику.**
  Например, подсчёт остатка занятий в абонементе — есть точная формула
  в `cabinet.html` (`computeRemaining`), и если бот считает то же самое —
  должен использовать идентичную логику, а не собственную. Расхождение
  в цифрах между ботом и кабинетом подрывает доверие.
